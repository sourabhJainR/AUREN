# Compiler engineering lessons from evidence-driven execution

This document records generalized lessons from a standalone compiler implementation campaign. It deliberately contains no dependency, import, or runtime coupling to the system that produced the observations.

## 1. Status claims must follow executable evidence
A compiler pipeline can have lexer, parser, semantic, IR, native execution, learning, and bootstrap modules while still not being self-hosting. The status model must distinguish implemented code, behaviorally verified code, deterministic replay, reproducible bootstrap, and true self-hosting. Do not collapse these into a single maturity flag.

## 2. CI failures are engineering evidence
A formatting failure before compilation is still a useful regression signal. The loop is implement -> CI -> inspect failing step -> minimal fix -> CI -> review -> merge. Record the exact gate that failed.

## 3. Test the claimed boundary
Useful compiler boundaries include source to tokens, tokens to AST, AST to semantic model, semantic model to ownership/effects, AST/IR to generated code, generated code to runtime result, formatter to parser round trip, and bootstrap stage to repeated bootstrap stage.

## 4. Differential checks need independent expectations
When two implementations are compared, the expected result must not be generated by copying the implementation under test. Prefer a small reference semantics, explicit fixtures, or independently constructed expected values.

## 5. Determinism is a first-class property
Stable IDs, serialized artifacts, normalized diagnostics, ordered maps, generated cases, and bootstrap fingerprints should be deterministic. Re-running the same input should produce the same observable artifact unless nondeterminism is explicitly part of the contract.

## 6. Learning must remain advisory
Persistent compiler learning can identify recurring diagnostics and successful repairs, but it must not silently change compiler authority, permissions, security policy, or acceptance gates. Verified findings can guide future tests; they cannot replace verification.

## 7. Structured concurrency needs static and runtime evidence
Static checks can prove task lifetime rules for source programs. Runtime tests must still prove cancellation, joining, failure propagation, scope cleanup, and absence of orphaned work.

## 8. Interop safety requires a narrow boundary
A safe Rust interoperability layer should start with a deliberately small supported type set, validate symbols and signatures, isolate unsafe calls, and verify generated wrappers. Expanding the type surface should require new ABI fixtures.

## 9. Fuzzing should target invariants
Random input volume is not enough. Generated cases should assert parse/format/parse identity, semantic preservation, deterministic output, safe lowering, and reference/native result agreement.

## 10. Completion is a chain of evidence
A durable work record should connect requirement -> implementation -> test -> CI -> review -> evidence -> regression coverage. Missing links should remain visible instead of being inferred.

## Reusable rule
For future engineering campaigns, prefer the smallest evidence-producing change that closes one acceptance gap, then immediately run the strongest cheap verification for that gap. Keep unrelated cleanup separate unless it is required for correctness.
